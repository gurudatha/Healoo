HEALOO REST API - DEVELOPER DOCUMENTATION: AUTHENTICATION AND USER API
=====================================================================

Applies to: care-api v0.2 (DataItem v2), design document sections 4 and 5, and
Documentation/DataItem_Design.md.
Note: the server code has not been compiled yet. This document describes the
behaviour written in the source; confirm it against a running server.

  2. Authentication
  3. Add user

1. BASICS
---------

Base URL
  LAN trial:   https://<computer's LAN IP>:8443
               (Android emulator: https://10.0.2.2:8443)
  Internet:    https://api.<your domain>

  All API paths start with /v1. GET /v1/config (no token needed) returns the
  API base, the WebSocket URL and which sign-in mode the server uses.

TLS on the LAN
  The trial server uses its own certificate authority. Pass its certificate
  to curl instead of turning checks off:
      curl --cacert healoo-local-ca.crt https://192.168.1.20:8443/healthz
  Get the file with:
      docker compose cp care-api:/data/tls/healoo-local-ca.crt .

Formats
  - Requests and responses are JSON (Content-Type: application/json),
    except file uploads, which send the raw file.
  - IDs are UUID strings. Item and message IDs are time-based UUIDs.
  - Every user also has a short Healoo ID such as HL-2M9P4 ("public_id").
  - Dates are "YYYY-MM-DD", clock times "HH:MM" (24-hour). Timestamps
    (sent_at, fires_at, created_at) are ISO-8601 with the offset, e.g.
    2026-09-21T20:00:00+05:30. Time zone defaults to Asia/Kolkata.
  - Optional fields that have no value are left out of responses, not
    sent as null.
  - Lists come wrapped as:  { "data": [ ... ], "page_state": null }
    (paging cursors are not implemented yet; page_state is always null).

Errors
  Every error has the same shape:
      {
        "error": {
          "code": "ACCESS_DENIED",
          "message": "no grant for this user",
          "request_id": "01J9..."
        }
      }

  HTTP  code             Meaning
  400   BAD_REQUEST      Invalid input; message says what to fix
  401   UNAUTHORIZED     Missing, invalid or expired token
  403   ACCESS_DENIED    Signed in, but not allowed (message gives the reason)
  404   NOT_FOUND        No such user, item, appointment, alert or grant
  409   CONFLICT         Conflicting change, e.g. adding to a closed item
  429   RATE_LIMITED     Too many requests
  500   INTERNAL         Server error; quote request_id when reporting it

Limits
  - 20 requests per second per user (bursts up to 40), then 429.
  - Request bodies up to 20 MB (files go through upload URLs, section 5).
  - Up to 20 attachments per item; images up to 10 MB, PDFs up to 25 MB.


2. AUTHENTICATION
-----------------

Every /v1 endpoint except /v1/config needs a bearer token:

    Authorization: Bearer <access_token>

The server accepts one of two token types, chosen by the server setting
AUTH_MODE. Check which one with GET /v1/config ("auth": {"mode": ...}).

2.1 Auth0 tokens (AUTH_MODE=auth0; required on the internet)
  - Issued by your Auth0 tenant for the API audience (default
    https://api.careconnect.local). Algorithm RS256.
  - The server checks the signature against the tenant's public keys
    (cached 10 minutes, refreshed when a new key ID appears), and checks
    "iss" (https://<AUTH0_DOMAIN>/), "aud" and "exp".
  - The mobile apps get tokens through Auth0 Universal Login with PKCE.
    For scripts, get a user token the same way, or with the Password grant
    if your tenant has it enabled:
        curl https://<AUTH0_DOMAIN>/oauth/token -H 'content-type: application/json' -d '{
          "grant_type": "password", "username": "<email>", "password": "<password>",
          "audience": "https://api.careconnect.local", "client_id": "<client id>",
          "scope": "openid profile email"
        }'
  - Custom claims (added by the Auth0 post-login Action, design doc 5.3):
        https://careconnect.local/roles   array of role names
        https://careconnect.local/uid     Healoo user_id, once provisioned
    The namespace is the server setting CLAIMS_NAMESPACE.
  - Access tokens last 15 minutes; renew them with the refresh token.

2.2 Developer tokens (AUTH_MODE=dev; LAN trial only)
  For offline testing. Refused by the server in internet mode.
  - Signed with the server's DEV_JWT_SECRET (HS256), iss and aud
    "healoo-dev", valid 12 hours. Same custom claims as Auth0 tokens.

  List the trial accounts (no token needed):
      GET /dev/users
      Response 200:
      { "data": [ { "public_id": "HL-2M9P4", "display_name": "Lakshmi K.", "role": "PATIENT" }, ... ] }

  Get a token for a trial account (no token needed):
      POST /dev/token
      { "public_id": "HL-2M9P4" }

      Response 200:
      {
        "access_token": "eyJhbGciOiJIUzI1NiIs...",
        "token_type": "Bearer",
        "expires_in": 43200,
        "user_id": "5eed0000-0000-4000-8000-000000000001"
      }
      404 if no user has that Healoo ID, or if the server isn't in LAN +
      dev mode (then /dev/* doesn't exist).

  From the command line (same DEV_JWT_SECRET as the server):
      devtoken <user_uuid> [role ...]

  Example:
      BASE=https://192.168.1.20:8443
      TOKEN=$(curl -s --cacert healoo-local-ca.crt -X POST $BASE/dev/token \
        -H 'content-type: application/json' -d '{"public_id":"HL-2M9P4"}' \
        | sed -E 's/.*"access_token":"([^"]+)".*/\1/')

2.3 What happens on every request
  1. The token is verified (2.1 or 2.2). Failure -> 401.
  2. The token subject ("sub") is mapped to a Healoo user. If none exists,
     one is created (section 3.1).
  3. The per-user rate limit is applied.
  4. The endpoint runs. What the user may see is decided by the server's
     access rules (design doc 2.3), using the database, not token roles.
     So a doctor who leaves a hospital loses access at once, even with a
     token issued earlier.

  Check your token:
      curl --cacert healoo-local-ca.crt $BASE/v1/me -H "authorization: Bearer $TOKEN"

2.4 WebSocket
  wss://<host>/v1/ws (or /ws). Send the token as the Authorization header,
  as ?token=<token>, or as the first frame {"type":"auth","token":"..."}
  within 10 seconds. The server closes the socket with code 4001 when the
  token expires; reconnect with a fresh token.


3. ADD USER
-----------

3.1 Create an account (self sign-up)
  There is no separate "create user" call. A user is created automatically
  the first time a valid token with a new "sub" calls any /v1 endpoint.
  New accounts always get the PATIENT role and a new Healoo ID.

  With Auth0: the person signs up on the Auth0 login page, then the app
  calls GET /v1/me.

  With developer tokens: make a token for a new UUID, then call /v1/me:
      NEW=$(uuidgen | tr A-Z a-z)
      TOKEN=$(devtoken $NEW patient)
      curl --cacert healoo-local-ca.crt $BASE/v1/me -H "authorization: Bearer $TOKEN"

  Response 200 (UserProfile):
      {
        "user_id": "3f6c...e21",
        "public_id": "HL-7QK4M",
        "display_name": "Dev user",
        "roles": ["PATIENT"],
        "headline": "Patient",
        "connected": true
      }

  If the token carries a "uid" claim for an existing user, the new "sub" is
  linked to that user instead of creating a new one.

  Other roles (DOCTOR, LAB, HOSPITAL, ASSISTANT, ADMINISTRATOR) are set up
  by administrators; there is no public API for that in v0.1. On the trial
  server they come from the seed data (care-seed).

3.2 Set the new user's profile
      PATCH /v1/me
      { "display_name": "Ravi Kumar", "location": "Kurnool" }

  - display_name: required, 1 to 80 characters.
  - location: optional; empty or missing clears it.
  Response 200: the updated UserProfile. 400 if the name is empty or too long.

3.3 Add a user to your contacts
  Adding a contact lets you message each other and see shared items. It
  does not give access to any records by itself; the owner still has to
  share items.

      POST /v1/connections
      { "user_id": "5eed0000-0000-4000-8000-000000000002" }

  Response 200: that user's UserProfile with "connected": true.
  400 if you try to add yourself; 404 if the user doesn't exist.
  Adding someone twice is harmless.

  Remove a contact:
      DELETE /v1/connections/{user_id}      -> 204 No Content

  Example:
      curl --cacert healoo-local-ca.crt -X POST $BASE/v1/connections \
        -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
        -d '{"user_id":"5eed0000-0000-4000-8000-000000000002"}'


4. QUERY USERS
--------------

Searches return profile fields only, never records or data items.

4.1 Search
      GET /v1/search?q=<text>&type=<role>

  q
    - A Healoo ID such as HL-7R2C9: exact match (case doesn't matter).
    - Otherwise name words: every word must appear in the name
      ("anitha rao" finds "Dr. Anitha Rao"). Titles such as "Dr" are ignored.
    - Empty: returns your contacts.
  type (optional)
    ALL (default), USER or PATIENT, DOCTOR, HOSPITAL, LAB, ASSISTANT,
    ADMINISTRATOR, APP_ADMINISTRATOR. Filters on the user's main role.

  You never appear in your own results. Up to 50 matches.

  Response 200:
      {
        "data": [
          {
            "user_id": "5eed0000-0000-4000-8000-000000000002",
            "public_id": "HL-7R2C9",
            "display_name": "Dr. Anitha Rao",
            "roles": ["DOCTOR"],
            "headline": "Doctor · General Medicine",
            "location": "[City]",
            "hospital": "Test Hospital A",
            "official_number": "REG-TEST-001",
            "connected": true
          }
        ],
        "page_state": null
      }

  Examples:
      curl --cacert healoo-local-ca.crt "$BASE/v1/search?q=HL-7R2C9" -H "authorization: Bearer $TOKEN"
      curl --cacert healoo-local-ca.crt "$BASE/v1/search?q=rao&type=DOCTOR" -H "authorization: Bearer $TOKEN"

4.2 One user's profile
      GET /v1/users/{user_id}
  Response 200: UserProfile ("connected" says whether they're in your
  contacts). 404 if not found.

4.3 Your contacts
      GET /v1/connections
  Response 200: { "data": [UserProfile, ...], "page_state": null }

4.4 Yourself
      GET /v1/me
  Response 200: your UserProfile.

UserProfile fields
  user_id          UUID
  public_id        Healoo ID, e.g. HL-2M9P4
  display_name     name shown to others
  roles            array; the main role comes first
  headline         e.g. "Patient", "Doctor · Test Hospital A"
  photo_uri        optional
  location         optional
  hospital         optional; current hospital of a doctor or administrator
  official_number  optional; doctor's registration number
  connected        true if this user is in your contacts


5. UPLOAD DOCUMENT
------------------

A document is a data item (for example a REPORT) with one or more images
or PDFs attached. Uploading takes three steps:

  Step 1  Ask for upload URLs          POST /v1/uploads/presign
  Step 2  Upload each file             PUT <upload_url>
  Step 3  Create the item              POST /v1/items

5.1 Step 1: ask for upload URLs
      POST /v1/uploads/presign
      {
        "files": [
          { "name": "cbc_page1.jpg", "mime": "image/jpeg",      "size": 482113 },
          { "name": "cbc_report.pdf", "mime": "application/pdf", "size": 1203344 }
        ]
      }

  - 1 to 20 files per call.
  - mime must be image/... (up to 10 MB) or application/pdf (up to 25 MB).
  - size is the file size in bytes.

  Response 200 (same order as the request):
      {
        "uploads": [
          { "upload_url": "https://192.168.1.20:8443/files/uploads/5eed.../01J9...-cbc_page1.jpg?m=PUT&exp=...&ct=image%2Fjpeg&sig=...",
            "uri": "obj:uploads/5eed0000-0000-4000-8000-000000000001/01J9...-cbc_page1.jpg" },
          { "upload_url": "https://...", "uri": "obj:uploads/.../01J9...-cbc_report.pdf" }
        ]
      }

  Keep each "uri"; you need it in step 3. Upload URLs expire after 10
  minutes. On the internet profile upload_url points at the files host
  (S3/MinIO) instead.

5.2 Step 2: upload each file
      PUT <upload_url>
      Content-Type: <the same mime as in step 1>
      Body: the raw file bytes (no JSON, no form encoding)

      curl --cacert healoo-local-ca.crt -X PUT "<upload_url>" \
        -H 'content-type: image/jpeg' --data-binary @cbc_page1.jpg

  200 on success. 403 if the URL has expired or was changed; 400 if the
  Content-Type doesn't match or the file is too large. No bearer token is
  needed: the URL itself carries a signature.

5.3 Step 3: create the item
  A data item is a container for one case. It starts from exactly one
  primary part (report, appointment, alert or message) and can then grow:
  people discuss it, add files, book visits and set reminders. The item has
  one owner (always a patient), one access list covering everything inside
  it, and one status.

      POST /v1/items
      {
        "owner_id": "5eed0000-0000-4000-8000-000000000001",
        "title": "CBC - Complete blood count",
        "keywords": ["CBC", "Haemoglobin"],
        "share_with": ["5eed0000-0000-4000-8000-000000000002"],
        "report": {
          "title": "CBC - Complete blood count",
          "attachments": [
            { "kind": "IMAGE", "uri": "obj:uploads/.../01J9...-cbc_page1.jpg",
              "mime": "image/jpeg", "size": 482113, "name": "cbc_page1.jpg" },
            { "kind": "PDF", "uri": "obj:uploads/.../01J9...-cbc_report.pdf",
              "mime": "application/pdf", "size": 1203344, "name": "cbc_report.pdf" }
          ],
          "links": ["https://example.com/lab-result/123"]
        }
      }

  Header fields
    owner_id     optional; defaults to you. Must be a PATIENT. Set it to a
                 patient's user_id to create an item for that patient.
    title        optional, max 120 characters. Default comes from the primary
                 part: the report title, "Appointment with Dr. ...", the
                 first line of the message, or the alert text.
    keywords     optional; up to 20
    share_with   optional user IDs to share with at once. A hospital account
                 creates a hospital-wide share. Only used when you are the owner.

  Primary part: send exactly one of these (otherwise 400):
    report       { title, attachments[], links[] }. At least one file or link.
                 Files are marked as report files (is_report = true).
    appointment  see 7.3 (patient_id must equal the owner)
    alert        see 7.4
    message      { body, client_msg_id, attachments[]? } starts a discussion

  Rules
    - Attachments must be files you uploaded yourself through step 1
      (otherwise 403). kind must match mime, and sizes must be within the
      limits (otherwise 400). The server numbers "position" in the order sent.
    - Creating for someone else: only DOCTOR, ASSISTANT and LAB users can,
      the owner must be a PATIENT in your contacts, and you get access to
      the item automatically. The patient decides any further sharing.
    - A LAB must set owner_id when creating a report.
    - Booking an appointment gives the doctor access automatically.
    - New items are always OPEN.

  Response 200: the new data item (section 6.5), with short-lived view URLs
  for its files. Image thumbnails, PDF page counts and SHA-256 hashes are
  added a moment later by the media worker; connected apps then receive an
  "item.updated" WebSocket event.

  Common errors
    400  "send exactly one of appointment, message, alert or report"
    400  "items belong to a patient: owner_id must be a patient"
    400  "a report needs at least one file or link"
    400  "<name> is not an allowed IMAGE (type or size)"
    403  "attachments must be files you uploaded"
    403  "you can create items only for patients in your contacts"

  Other ways to start an item (examples)
      Appointment:
      { "appointment": { "patient_id": "<patient>", "doctor_id": "<doctor>",
          "date": "2026-10-05", "time": "11:30",
          "recurrence": { "frequency": "BIWEEKLY", "period": "THREE_MONTHS" } } }

      Alert (owned by you):
      { "title": "Evening medicine",
        "alert": { "type": "MEDICATION", "text": "Iron tablet after dinner",
                   "date": "2026-09-21", "time": "20:00",
                   "recurrence": { "frequency": "DAILY", "period": "ONE_MONTH" } } }

      Message (new discussion with a doctor; the patient owns it):
      { "share_with": ["<doctor>"],
        "message": { "body": "Here are my BP readings.", "client_msg_id": "c-001" } }


6. READ AND LIST DATA ITEMS
---------------------------

6.1 List items you can see
      GET /v1/items?status=OPEN&kind=REPORT&limit=20

  status   OPEN (default) or CLOSED
  kind     optional: APPOINTMENT, MESSAGE, ALERT, REPORT or ATTACHMENT.
           Matches any part the item contains, not only the primary kind.
  limit    1 to 100, default 20

  Includes, most recently updated first:
    - items you own;
    - items shared directly with you;
    - for doctors: items shared with a hospital where you currently work;
    - for assistants: items of patients your doctor delegated to you.

  List entries are headers with counts; the child lists (messages,
  attachments, appointments, alerts, links) are empty and access_list is
  empty. Use GET /v1/items/{id} for the full item. The kind filter is
  applied after the limit, so a filtered list can be shorter than "limit".

  Example:
      curl --cacert healoo-local-ca.crt "$BASE/v1/items?status=OPEN&limit=50" \
        -H "authorization: Bearer $TOKEN"

6.2 One item
      GET /v1/items/{item_id}

  Returns the header plus the child lists: the latest 100 messages, all
  attachments (view URLs valid for 10 minutes), appointments with their
  next 12 visits, and the alerts you may see. What you get depends on your
  access to the whole item:
    - Full access: everything. You see your own alerts; the owner sees all.
    - Metadata only (for example an assistant without delegation, or an
      item with report files shared with someone who isn't a doctor):
      header, keywords, status and appointment dates/times/doctor only; no
      messages, files, links, notes or alerts. allowed_actions is ["meta"].
    - No access: 403 with the reason, e.g. "no grant for this user" or
      "hospital grant, but no active affiliation with that hospital".
  Every decision is recorded in the audit log.

6.3 Change the title or keywords (owner only)
      PATCH /v1/items/{item_id}
      { "title": "CBC and follow-up", "keywords": ["CBC", "Iron"] }

6.4 Other item lists
      GET /v1/users/{user_id}/shared-items
        Open items shared between you and that user, both ways. Empty
        unless the user is in your contacts.
      GET /v1/dashboard
        { "open_reports": 1, "unread_messages": 2, "upcoming_appointments": 1 }
        open_reports = open items with report files; upcoming_appointments =
        scheduled visits in the next 7 days.

6.5 Data item fields
  item_id           time-based UUID
  owner_id          the patient who owns the item
  primary_kind      APPOINTMENT, MESSAGE, ALERT or REPORT; fixed at creation
  kinds             parts the item contains now: APPOINTMENT, MESSAGE,
                    ALERT, REPORT, ATTACHMENT
  title, keywords   text
  status            OPEN or CLOSED
  closure           only when CLOSED: closed_at, closed_by, feedback?,
                    rating? (1-5, only ever set by the patient)
  access_list       who it is shared with; only shown to the owner. Each:
                    grant_id, grantee_type (USER or HOSPITAL), grantee_id,
                    grantee_name, via_hospital_id (optional)
  counts            messages, attachments, appointments, alerts,
                    unread_messages (for you)
  messages          Message list (7.1), oldest first
  attachments       Attachment list (7.2), in display order
  appointments      Appointment list (7.3)
  alerts            Alert list (7.4)
  links             https links added with a report
  created_by_name, created_at, updated_at
  allowed_actions   what you may do: read, message, attach, book, alert,
                    close, share, revoke, rate, reopen, or meta

  Example (full access, shortened):
      {
        "item_id": "8a4b1c20-7f2e-11f1-9c3d-2b1f5e7a9d01",
        "owner_id": "5eed0000-0000-4000-8000-000000000001",
        "primary_kind": "REPORT",
        "kinds": ["REPORT", "APPOINTMENT", "MESSAGE", "ALERT", "ATTACHMENT"],
        "title": "CBC - Complete blood count",
        "keywords": ["CBC", "Haemoglobin"],
        "status": "OPEN",
        "access_list": [ { "grant_id": "...", "grantee_type": "USER",
                           "grantee_id": "5eed...0002", "grantee_name": "Dr. Anitha Rao" } ],
        "counts": { "messages": 2, "attachments": 4, "appointments": 1, "alerts": 4, "unread_messages": 1 },
        "messages": [ ... ], "attachments": [ ... ], "appointments": [ ... ], "alerts": [ ... ],
        "links": [],
        "created_by_name": "City Diagnostics",
        "created_at": "2026-09-20T09:02:11+05:30",
        "updated_at": "2026-09-21T10:14:02+05:30",
        "allowed_actions": ["read", "message", "attach", "book", "alert", "close", "share", "revoke", "rate"]
      }


7. WORKING INSIDE AN ITEM
-------------------------

Adding anything needs full access to the item, and the item must be OPEN
(409 "this item is closed; reopen it to add to it"). Every change sends
"item.updated" to everyone with access.

7.1 Messages (every message belongs to an item)
      GET  /v1/items/{item_id}/messages?limit=100
      POST /v1/items/{item_id}/messages
      { "body": "Haemoglobin is slightly low.", "client_msg_id": "c-7f2a",
        "attachments": [ ...optional files from /v1/uploads/presign... ] }

  - Reading marks the discussion as read for you.
  - body 1-4000 characters. client_msg_id (max 64 characters) makes
    sending safe to retry: resending the same one returns the first message.
  - Files sent with a message also appear in the item's attachments.
  - Everyone with full access to the item can read and write. A discussion
    between a patient and two doctors works when both are on the access list.
  Message fields: message_id, item_id, sender_id, body, sent_at, attachment_ids

7.2 Attachments
      GET  /v1/items/{item_id}/attachments
      POST /v1/items/{item_id}/attachments
      { "attachments": [ { "kind": "PDF", "uri": "obj:uploads/...", "mime": "application/pdf",
                           "size": 90211, "name": "discharge.pdf" } ],
        "is_report": false }

  - Upload the files first (5.1, 5.2). Up to 20 per request.
  - is_report = true marks them as report files. Report files make the
    item readable in full only by doctors (other grantees get metadata).
  Attachment fields
    attachment_id, kind (IMAGE or PDF), uri (view URL, 10 minutes; read the
    item again for a new one), mime, size, position, name, page_count and
    thumb_uri and sha256 (once processed), added_by, added_at,
    message_id (if posted in a message), is_report

7.3 Appointments
      POST /v1/items/{item_id}/appointments
      {
        "patient_id": "5eed0000-0000-4000-8000-000000000001",
        "doctor_id":  "5eed0000-0000-4000-8000-000000000002",
        "date": "2026-10-05",
        "time": "11:30",
        "timezone": "Asia/Kolkata",
        "duration_min": 15,
        "hospital_id": "5eed0000-0000-4000-8000-000000000003",
        "notes": "Haemoglobin review",
        "recurrence": { "frequency": "BIWEEKLY", "period": "THREE_MONTHS" }
      }

  Fields
    patient_id    required; must be the item's owner
    doctor_id     required; must be a DOCTOR. Gets access to the item.
    date, time    required; first visit, not in the past
    timezone      optional IANA name; default Asia/Kolkata
    duration_min  optional 5-240; default 15
    hospital_id   optional; a hospital the doctor works at
    notes         optional, max 500 characters
    recurrence    optional; leave out for a single visit
      frequency   DAILY, WEEKLY, BIWEEKLY, MONTHLY or QUARTERLY
      period      ONE_MONTH, TWO_MONTHS, THREE_MONTHS or SIX_MONTHS;
                  leave out to repeat until cancelled

  Who can book: the patient, the doctor, or the doctor's assistant.

  Repeat rules
    - Visits are the first date, then every step (1 day, 7 days, 14 days,
      1 month, 3 months) while the visit date is before date + period.
    - MONTHLY and QUARTERLY keep the day of the month; if the month is
      shorter, the visit falls on its last day.
    - Combinations giving only one visit are refused (400): MONTHLY for
      1 month, QUARTERLY for 1, 2 or 3 months. Book a single visit instead.
    - DAILY needs a period.
    Visits for a start on 1 Oct:
                 1 month  2 months  3 months  6 months  no period
      Daily        31       61        92       182      refused
      Weekly        5        9        14        26      until cancelled
      Bi-weekly     3        5         7        13      until cancelled
      Monthly    refused     2         3         6      until cancelled
      Quarterly  refused  refused   refused      2      until cancelled

  Automatic reminders: APPOINTMENT_REMINDER alerts for the patient (1 day
  and 1 hour before each visit) and for the doctor (1 hour before).

  Change the series (future visits only)
      PATCH /v1/items/{item_id}/appointments/{appointment_id}
      { "date": "2026-10-06", "time": "10:00", "duration_min": 20, "notes": "...",
        "recurrence": { "frequency": "WEEKLY", "period": "TWO_MONTHS" } }
    Send "recurrence": null to turn a series into a single visit. The rule
    you send replaces the old one. { "status": "CANCELLED" } cancels the
    whole series and its reminders.

  One visit
      POST /v1/items/{item_id}/appointments/{appointment_id}/visits/{date}
      { "action": "MOVED", "new_date": "2026-10-20", "new_time": "10:00" }
    {date} is the visit's original_date. action is one of:
      CANCELLED   patient, doctor or assistant
      MOVED       patient, doctor or assistant; needs new_date and/or new_time
      COMPLETED   doctor or assistant (attended)
      NO_SHOW     doctor or assistant (missed)
    The rest of the series doesn't change.

  Appointment fields
    appointment_id, item_id, patient_id, doctor_id, doctor_name,
    hospital_id?, date, time, timezone, duration_min, notes?, recurrence?,
    exceptions [ { date, action (CANCELLED or MOVED), new_date?, new_time? } ],
    status (SCHEDULED, COMPLETED or CANCELLED), visit_count (absent when it
    repeats until cancelled), visits: the next 12 visits, each
    { date, time, original_date, status: SCHEDULED | COMPLETED | CANCELLED | NO_SHOW }

  Common errors
    400  "daily repeats need a period (1, 2, 3 or 6 months)"
    400  "this repeat and period give only one visit; book a single appointment instead"
    400  "patient_id must be the item's owner"
    400  "the first visit can't be in the past"
    403  "only the patient, the doctor or the doctor's assistant can book"

7.4 Alerts
      GET    /v1/items/{item_id}/alerts
      POST   /v1/items/{item_id}/alerts
      { "type": "MEDICATION", "text": "Iron tablet after dinner",
        "for_user": "5eed0000-0000-4000-8000-000000000001",
        "date": "2026-09-21", "time": "20:30", "timezone": "Asia/Kolkata",
        "recurrence": { "frequency": "DAILY", "period": "ONE_MONTH" } }
      DELETE /v1/items/{item_id}/alerts/{alert_id}

  - type: MEDICATION, APPOINTMENT_REMINDER, FOLLOW_UP, RESULT_READY or CUSTOM
  - text 1-200 characters; for_user defaults to you and must have access.
  - recurrence follows the same rules as appointments.
  - The server sends each firing as a push notification and an "alert"
    WebSocket frame. Removing needs the owner or the alert's recipient.
  Alert fields: alert_id, item_id, type, text, for_user, fires_at (first
  firing), timezone, recurrence?, appointment_id? (for reminders), active

7.5 Close and reopen
      POST /v1/items/{item_id}/close
      { "feedback": "Explained everything clearly.", "rating": 5 }

      POST /v1/items/{item_id}/reopen

  - Anyone with full access may close, with optional feedback (max 1000
    characters). rating (1-5) is accepted only when the patient closes
    their own item; from anyone else it is refused (400).
  - Closing cancels future visits and stops alerts.
  - Reopen: the owner or a treating doctor. The previous closure is kept in
    history; future visits aren't restored, so book again if needed.


8. MESSAGES TAB, CALENDAR AND LIVE UPDATES
------------------------------------------

8.1 Conversations (replaces /v1/threads)
      GET /v1/conversations
      GET /v1/conversations?with={user_id}

  One row per item with messages, per other person:
      { "item_id": "...", "item_title": "Latest BP readings", "primary_kind": "MESSAGE",
        "other_user": { ...profile... }, "last_message": "Sure, I will upload them tonight.",
        "last_message_at": "2026-09-22T10:50:00+05:30", "unread": 1 }
  Open one with GET /v1/items/{item_id}/messages. To start a new
  conversation, create a MESSAGE item (5.3). The patient in the pair owns
  it: a doctor writing to a patient sets owner_id to the patient.

8.2 Calendar
      GET /v1/appointments?from=2026-10-01&to=2026-10-31
  Upcoming visits across all your items: patients see their own visits,
  doctors see visits booked with them. Range up to 62 days (default: today
  to 30 days ahead).
      { "starts_at": "2026-10-05T11:30:00+05:30", "appointment_id": "...", "item_id": "...",
        "item_title": "CBC - Complete blood count", "with_user_id": "...",
        "with_user_name": "Dr. Anitha Rao", "status": "SCHEDULED" }

8.3 WebSocket (wss://<host>/v1/ws)
  Send {"type":"auth","token":"<access token>"} within 10 seconds. The server
  closes with code 4001 when the token expires; reconnect with a fresh one.
  Frames from the server:
      {"type":"message.new","item_id":"...","message":{...}}
      {"type":"item.updated","item_id":"...","change":"message"}
          change: created, message, attachment, appointment, alert,
                  closed, reopened, shared, updated
      {"type":"alert","item_id":"...", ...}
      {"type":"typing","item_id":"...","user_id":"..."}
      {"type":"ping"}   answer with {"type":"pong"}
  Frames you can send:
      {"type":"message.send","item_id":"...","body":"...","client_msg_id":"..."}
          answered with {"type":"message.sent","client_msg_id":"...","message":{...}}
      {"type":"typing","item_id":"..."}
